# Частина 1. Олександр перевіряє код Єгора (завдання 1, 2, 5)

## Завдання 1 (SRP)

Загалом норм. Клас розбитий нормально: причини для зміни виписані, кожна має свій клас, а `MedicalReportService` справді лише викликає інших по черзі й сам нічого не рахує. Сподобалось, що є `Locale.ROOT` (щоб в JSON було 24.69, а не 24,69) і перевірка `patientId`, бо він іде в назву файлу.

Що не так:

1. 🔴 Якщо в пацієнта `fullName = null`, програма падає з `NullPointerException`. Валідатор ім'я не перевіряє, а форматер потім викликає на ньому `.replace()`. Ми це запустили, воно реально падає. Те саме з `doctorPhone`: якщо він `null`, у SMS піде слово «null». Треба додати ці перевірки у валідатор.
2. 🟡 `MedicalReportService` сам створює помічників через `new`. Для SRP це нормально, але препод може сказати, що це суперечить DIP. Відповідь: у завданні 1 треба було просто розділити відповідальності, а інверсію ми показуємо окремо в завданні 5.
3. 🟡 Раніше при помилці запису файлу код просто писав помилку й ішов далі, а тепер виняток летить вгору. Це ми зробили спеціально (простіше й fail-fast), але треба вміти це пояснити.
4. 🟢 Метод `validate` довгий, п'ять перевірок підряд (складність 10). Можна розбити, але не критично.
5. 🟢 В JSON екрануються тільки лапки, а зворотний слеш ні.

## Завдання 2 (OCP)

Загалом норм. Точка розширення зрозуміла (`DiscountStrategy`), калькулятор не має `if` за типом клієнта, а `PARTNER` додається одним рядком у `Main`. Цифри збігаються зі старим кодом, це перевірено.

Що не так:

1. 🔴 `new DiscountCalculator(new HashMap<>())` падає з помилкою `Specified map is empty`. Так працює `EnumMap`, якщо дати йому порожню мапу. Ми це теж запустили. Легко виправити: створити порожній `EnumMap` і зробити `putAll`.
2. 🟡 Щоб додати нову категорію, довелось додати константу в `enum`. Калькулятор не змінювався, але enum теж існуючий код. Відповідь: це просто список назв без логіки.
3. 🟡 У `Order` пропала перевірка від'ємної суми й `null` (раніше була). Це суперечить fail-fast, варто повернути.
4. 🟢 Ставки записані рядками (`"0.10"`, `"0.15"`), «магічні числа». Можна винести в константи.

## Завдання 5 (DIP)

Загалом норм. Є три інтерфейси, залежності йдуть через конструктор з `requireNonNull`, у менеджері немає `new` для інфраструктури (ми перевірили пошуком), збірка в `Main`, Service Locator нема.

Що не так:

1. 🟡 Fail-fast тільки частково: `userId` перевіряється, а `email` ні. З `null` сповіщення піде в нікуди. Треба додати перевірку.
2. 🟡 У методичці приклад «ProductionRepository vs MockRepository», а в нас фальшиві залежності це лямбди в `Main`, окремого класу `Mock...` нема. Це теж реалізація інтерфейсу, але якщо хочеться ближче до тексту методички, можна винести в клас.
3. 🟢 Порядок кроків: база, потім кеш, потім лист. Якщо лист не пішов, база вже оновлена. Для лаби нормально, але можуть спитати про транзакції.

**Підсумок для Єгора:** принципи застосовані правильно. Треба виправити валідатор (завдання 1), конструктор калькулятора й `Order` (завдання 2) та перевірку `email` (завдання 5).

# Частина 2. Єгор перевіряє код Олександра (завдання 3, 4)

## Завдання 3 (LSP)

Загалом норм. Порушення зрозуміле: PDF «тільки для читання» кидав винятки, а редактор думав, що це звичайний документ. Ієрархію розділили на `Document` (читати й друкувати) і `EditableDocument` (ще й змінювати та зберігати). 2. 🟡 Контракт (що не можна передавати `null`, що після `setContent` треба повертати нове значення) записаний лише коментарем, а перевіряє його тільки `requireNonNull`. Для Java нормально, але можуть спитати «де це гарантується».
3. 🟢 `setContent(null)` кидає `NullPointerException`, а не `IllegalArgumentException`. Обидва підходять, а `requireNonNull` прямо названий у методичці.
4. 🟢 Документ сам друкує в консоль (`print`, `save`). Для SRP це дрібниця, в оригіналі було так само.
5. 🟢 `TextDocument` і `ReadOnlyPdfDocument` мають схожі поля й гетери, трохи дублювання.

## Завдання 4 (ISP)

Загалом норм. Великий інтерфейс на 8 методів розрізаний на 5 маленьких ролей, заглушок `UnsupportedOperationException` немає зовсім.
